# 正式安装首次启动恢复设计

## 目标

正式安装包启动时，即使本地 WebView 早于 Rust 管理状态就绪，或设置目录保留了历史失败激活回执，也应自动启动当前有效的 DSH deployment；界面不得把暂未读取的桌面更新状态误报为“更新通道尚未配置”。

## 已确认根因

- 本地启动页的三个初始化任务只尝试一次事件订阅与状态快照。初始化窗口内的瞬时 IPC 失败会永久呈现 `status_unavailable` 或前端默认状态。
- `load_single_confirmed_pending` 用 `activation_retry_available` 标记历史失败候选需要显式重试；冷启动流程目前直接传播该错误，连已经生效的权威 deployment 也不会启动。
- 桌面更新前端把通用初始状态 `unavailable` 文案写成“客户端更新通道尚未配置”。已安装 0.1.18 二进制包含正式更新端点，持久化桌面状态也是 `up_to_date`，因此该文案不能用于判断构建配置。

## 设计

### 启动页状态同步

启动页使用一个有限次数、短间隔的异步重试边界执行初次事件订阅和状态快照。调用成功后保持现有“先监听、后快照、事件优先”的竞态封闭规则；一次失败不得立即显示永久错误。重试耗尽后仍使用固定安全文案，不显示 bridge 动态错误正文。

### 历史失败激活

`activation_retry_available` 只禁止自动重放失败候选，不表示当前 deployment 不可启动。冷启动遇到该状态时读取权威 `deployment.json`：存在有效 deployment 就启动它，同时保留恢复提示；未安装则保持本地页；deployment 损坏仍进入 `activation_recovery_required`，不降低安全校验。

### 桌面更新初始文案

`unavailable` 表示尚无可呈现的稳定检查结果，改为“尚未检查客户端更新”。真正的网络、元数据、签名与安装错误继续由现有 `failed` 分支呈现。

## 范围

- 不新增生产依赖。
- 不删除或迁移任何用户状态文件。
- 不改变签名、manifest、来源校验、单调 revision 或激活候选确认规则。
- 通过 TypeScript 单元测试和 Rust 冷启动决策测试覆盖回归。
