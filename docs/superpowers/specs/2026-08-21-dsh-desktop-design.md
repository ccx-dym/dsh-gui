# DSH Desktop Windows 客户端设计

## 1. 背景与目标

DeepSeek Harness（以下简称 DSH）目前通过
`npx @deepseek-ai/dsh web` 启动本地 Web 服务，并在默认浏览器中打开
WebUI。该方式要求用户准备 Node.js、打开终端并管理后台进程，不符合普通
Windows 桌面软件的使用习惯。

本项目构建一个可安装的 Windows 桌面客户端，在不 fork、不修改官方 DSH
包的前提下，自动管理其启动、窗口、托盘、兼容更新和故障恢复。客户端还提供
可选的沉浸式图片皮肤。首个版本面向个人和小范围测试使用，强调较低资源占用、
官方功能完整性和数据安全。

## 2. 已确认范围

首个版本支持：

- Windows 10/11 x64；
- Tauri 2、Rust 和系统 WebView2；
- 仅当前用户安装，无需管理员权限；
- 独立桌面窗口与系统托盘；
- 关闭主窗口时隐藏到托盘，托盘“退出”才终止 DSH；
- 官方 WebUI 原样运行，并叠加可关闭的沉浸式皮肤适配层；
- 原创鲸鱼主题应用图标及 Windows 多尺寸图标集；
- 软件预定义且与命令行版隔离的数据目录；
- 精简在线安装包，首次运行时下载签名的兼容运行时；
- 桌面壳更新、官方版本发现、兼容版 DSH 更新和失败回滚；
- Windows 通知、日志、启动错误页和手动重启。

首个版本不支持：

- macOS、Linux、Windows ARM64 或 Windows 7；
- 多用户安装、管理员安装或企业集中部署；
- 完整离线安装包；
- 商业 Windows 代码签名；
- fork 或修改官方 DSH 源码；
- 与现有命令行 DSH 实例共享数据目录；
- 从现有 DSH 自动导入数据；
- 自定义数据根目录；
- 未验证即安装 npm 上的 DSH 最新版本。

## 3. 总体架构

系统由桌面壳和兼容运行时两部分组成：

```text
DSH Desktop（Tauri 2 / Rust）
├── 主窗口：单个 WebView2，直接加载官方 DSH WebUI
├── 生命周期：单实例、托盘、隐藏、恢复和退出
├── 服务管理：启动、探活、监控和停止 DSH
├── 皮肤管理：图片、遮罩、模糊和版本适配
└── 更新管理
    ├── 桌面壳更新
    └── 兼容运行时更新、验证和回滚

兼容运行时
├── 固定版本的 Node.js x64
├── 官方 @deepseek-ai/dsh
└── 对应的生产依赖
```

桌面壳不会重新实现 DSH，也不会代理或改写其业务请求。它以官方支持的
`web --no-open` 方式启动一份 DSH，并让 WebView2 访问仅绑定到
`127.0.0.1` 的本地服务。用户不需要安装 Node、npm 或全局 DSH。

运行时发布包由项目发布流程预先构建和验证。客户端只下载、校验和解压该包，
不在用户电脑上执行动态的 `npm install`。这样既能固定 Node 与依赖组合，也能
保留前一运行时用于回滚。

## 4. 进程与生命周期

### 4.1 启动流程

1. 桌面主进程取得单实例锁。已有实例存在时，新实例只唤醒原窗口。
2. 检查 WebView2、桌面配置和当前兼容运行时。
3. 没有运行时时进入首次下载页；已有运行时时继续启动。
4. 在回环接口上选择一个当前可用端口，避免固定端口冲突。
5. 用固定参数和预定义环境启动 Node 与 DSH，不打开外部浏览器。
6. 异步读取标准输出和标准错误，并轮询本地服务探活端点。
7. 服务就绪后再让主 WebView2 导航到 WebUI；此前显示本地启动页。
8. 服务失败或超时时显示错误摘要、重试、重启和打开日志入口。

WebView2 的初始化和页面操作不能阻塞 UI 线程。服务启动、更新、文件校验和日志
处理都在后台任务中执行，通过类型化事件向界面报告状态。

### 4.2 进程回收

桌面进程通过 Windows Job Object 管理 DSH 子进程树。桌面主进程异常终止时，
系统回收关联的 Node 和 DSH 子进程，避免残留后台服务。隐藏到托盘只是窗口状态
变化，不会结束 Job Object 或正在运行的 Agent 任务。

用户从托盘选择“退出”时，客户端先请求 DSH 正常停止并等待有限时间。仍有任务
运行时必须提示中断风险。正常停止超时后才终止完整子进程树，然后退出桌面壳。

### 4.3 托盘菜单

首个版本包含：

- 打开 DSH；
- 隐藏窗口；
- 选择或设置皮肤；
- 重启 DSH；
- 检查兼容更新；
- 打开日志目录；
- 退出。

默认不随 Windows 登录启动，用户可在设置中启用。该设置只控制桌面壳；DSH
仍由桌面壳统一启动和停止。

## 5. 数据与目录

程序使用固定的当前用户目录：

```text
%APPDATA%\DSH Desktop\
├── dsh-home\        # DSH 配置、凭据引用、会话和工作区记录
├── settings\        # 桌面、通知和皮肤设置
└── logs\            # 桌面端和 DSH 启动日志

%LOCALAPPDATA%\DSH Desktop\
├── runtimes\        # Node 与兼容版 DSH
├── skins\           # 客户端托管的皮肤图片
├── updates\         # 下载与验证暂存区
└── webview-data\    # WebView2 用户数据和缓存
```

固定数据根目录不限制用户选择工作区；用户仍可在官方 WebUI 中添加任意有权限的
本地项目目录。桌面版不读取或修改现有的 `~/.dsh`，也不触碰通过 npm 或其他
方式安装的全局 DSH。

API Key、模型、会话和工作区信息继续由官方 DSH 管理。桌面壳只持久化窗口、
皮肤、通知、版本和启动行为等自身设置。日志不得记录密钥、完整鉴权头或用户提示
正文；错误上下文仅保留诊断所需的版本、阶段、错误类型和 trace ID。

## 6. 沉浸式图片皮肤

### 6.1 用户能力

用户通过 Windows 原生文件选择器选择 PNG、JPG、JPEG 或 WebP 图片。图片经
格式、大小和分辨率校验后复制到应用皮肤目录，因此原文件移动或删除不会使当前
皮肤失效。

首个版本提供：

- 选择、更换和恢复默认皮肤；
- 覆盖、适应、拉伸、居中四种填充方式；
- 图片位置；
- 背景模糊程度；
- 深色或浅色遮罩及其透明度；
- 内容面板透明度；
- 启用或停用沉浸模式；
- 设置窗口内实时预览。

单张图片最大 20 MB、最大分辨率 8K。背景图片位于独立合成层，模糊仅作用于
背景而不作用于文字和控件，滚动时不重复解码图片。

### 6.2 注入边界

皮肤适配由桌面壳在文档加载早期注入，只改变背景、表面透明度、边框和必要的
可读性变量。它不得：

- 修改 DSH 安装文件；
- 拦截或改变会话、模型、工具与审批请求；
- 修改页面业务状态；
- 向官方页面暴露进程启动、任意文件访问或更新权限。

皮肤通过只读内部资源协议加载。该协议只允许访问应用已登记的当前皮肤文件，URL
参数不能转换为任意文件系统路径。

### 6.3 兼容降级

每个兼容 DSH 版本绑定一个皮肤适配版本。页面加载后检查关键结构和适配状态；
检查失败时撤销沉浸样式并回到官方界面。设置页显示当前版本“已验证”或“未验证”。
任何皮肤错误只能降低视觉效果，不能阻断 DSH 启动或 Agent 操作。

### 6.4 应用图标

应用采用原创鲸鱼主题图标：独立的明亮天空蓝鲸鱼轮廓配浅蓝尾鳍和腹部装饰，
鲸身内置圆润的白色 `H`，表达 Harness。明亮配色用于营造轻快、开放的桌面体验，
避免深色主体带来的压抑感。图标不复制 DeepSeek 官方鲸鱼的具体线条、比例或构图，
也不使用官方文字标识。关于页需要明确标注本项目是非官方社区桌面客户端。

图标使用透明背景和居中的方形构图。鲸鱼轮廓是 16×16 和托盘尺寸的主要识别
元素；`H` 在极小尺寸下允许退化为辅助高光，不依赖其保持可读。项目资产包括：

- `assets/icons/dsh-desktop-source.png`：1254×1254 RGBA 源图；
- `assets/icons/dsh-desktop.ico`：包含 16、20、24、32、40、48、64、128 和
  256 像素的 Windows ICO；
- `assets/icons/icon-<size>.png`：上述各尺寸的独立 PNG，用于托盘、通知、窗口、
  安装器和自动化视觉检查。

发布前需要在 Windows 浅色与深色主题、100% 与高 DPI 缩放、开始菜单、任务栏、
托盘和通知中分别检查轮廓与边缘。任何后续图标重制都必须保留原创性，并重新生成
完整尺寸集，不能让 Windows 在运行时从单一大图临时缩放全部尺寸。

## 7. 更新与通知

### 7.1 更新通道

更新分为三个相关但独立的状态：

1. **官方版本发现**：从 npm 包元数据发现官方 DSH 新版本，只通知“等待兼容
   验证”，不允许直接安装。
2. **兼容运行时更新**：项目签名的兼容清单列出已验证的 Node、DSH、依赖和
   皮肤适配组合，用户确认后下载。
3. **桌面壳更新**：Tauri 桌面程序通过独立的签名更新清单升级。

静态更新清单和发布包通过 HTTPS 提供，可放置在 GitHub Releases 等静态发布
源。具体根地址由构建配置注入，不在业务代码中硬编码。运行时清单至少包含：

- DSH、Node、桌面壳最低版本和皮肤适配版本；
- 平台与架构；
- 包大小、SHA-256 摘要、下载地址和发布签名；
- 发布说明、验证时间和兼容测试摘要。

### 7.2 更新流程

1. 下载到新的暂存目录；下载失败不修改当前状态。
2. 验证 HTTPS 来源、发布签名、摘要、平台和版本约束。
3. 解压到新的版本目录，不覆盖当前运行时。
4. 复制当前 DSH 数据作为升级验证副本。
5. 使用验证副本启动新版，执行服务探活、配置加载、WebUI 加载和基础会话检查。
6. 全部通过后通知用户重启切换；Agent 任务运行期间不得切换。
7. 首次正式启动失败时自动恢复旧运行时和更新前数据指针。

DSH 当前仍处于 developer preview，持久化 schema 不承诺跨版本迁移。因此旧运行时
和升级前数据快照必须保留。用户已在新版产生新会话后手动回退时，客户端要明确
说明旧版可能无法读取新版数据；新版数据继续保留但不自动合并。

旧运行时、快照和皮肤历史不静默删除。设置页显示其占用空间，并提供需要明确确认
的清理操作。

### 7.3 通知策略

- 启动后延迟检查一次，不阻塞启动；
- 托盘驻留时默认每 12 小时检查；
- 同一版本和同一状态只发送一次 Windows 通知；
- 断网、超时和发布源临时异常保持静默，并在下个周期重试；
- 设置页和托盘始终可查看当前版本、官方最新版和兼容最新版；
- 用户可以关闭通知或手动检查；
- 下载可以在后台进行，安装与切换必须经用户确认。

## 8. 安装与卸载

Tauri 2 使用 NSIS 生成当前用户模式的 `setup.exe`。安装器创建开始菜单和可选
桌面快捷方式，不触发 UAC。它检测 WebView2；缺失时使用微软 Evergreen
Bootstrapper 安装共享 Runtime。首个安装包只包含桌面壳、图标和启动资源，Node
与兼容 DSH 在首次启动时下载。

首次下载遇到断网、超时、磁盘不足、代理或校验失败时，页面显示明确原因、重试和
日志入口。未完成的暂存包不能成为当前运行时。

默认卸载行为为：

- 删除桌面程序、快捷方式、桌面版专用 Node、DSH 运行时和可下载缓存；
- 保留 DSH 会话、模型配置、桌面设置和皮肤；
- 不删除系统共享 WebView2；
- 不删除全局 DSH、`~/.dsh` 或任何外部工作区。

卸载器提供独立的“同时删除所有用户数据”选项，列出准确目录并要求再次确认。
重新安装时若发现保留数据，应复用该数据并重新下载当前兼容运行时。

## 9. 错误处理与安全

所有外部操作必须设置超时并返回结构化错误，不使用裸异常捕获。关键错误类型包括：

- WebView2 缺失或初始化失败；
- 回环端口不可用、服务探活超时或 DSH 非零退出；
- 下载断开、代理失败、磁盘不足、签名或摘要错误；
- 数据快照失败、运行时切换失败或回滚失败；
- 皮肤文件损坏、不支持、过大或内部协议加载失败。

安全边界如下：

- DSH 仅监听回环接口，不暴露局域网地址；
- 动态端口不能被视为身份验证手段，桌面壳仍需限制 WebView 导航和外部链接；
- WebView 页面不获得通用 Tauri shell、文件系统或更新能力；
- sidecar 参数采用固定模板和严格校验，不拼接 shell 命令；
- 运行时和桌面更新都必须验证发布签名与摘要；
- 外部链接交给系统浏览器，主窗口只允许本地 DSH 来源和应用内部页面；
- 日志滚动、限制大小并脱敏，关键事件携带 trace ID、阶段、耗时和重试次数。

## 10. 性能目标

性能以目标 Windows 电脑的实测结果为准，首个版本采用以下验收基线：

- 已安装兼容运行时后，普通 SSD 电脑冷启动 5 秒内显示可交互窗口，10 秒内完成
  DSH 就绪；
- 桌面壳空闲 CPU 接近 0%，隐藏到托盘后不持续轮询或渲染页面动画；
- 只运行一个主 WebView2、一个桌面主实例和一份 DSH；
- 皮肤启用前后分别记录启动耗时、内存和滚动表现，不允许出现明显交互卡顿；
- 4K/8K 背景使用单独 GPU 合成层，页面滚动不重复解码；
- 更新检查和下载不阻塞 UI、流式输出或 Agent 任务。

## 11. 测试与验收

测试优先隔离真实外部服务，使用模拟 DSH 服务、模拟更新清单和临时数据目录。
需要覆盖：

- Windows 10 x64 与 Windows 11 x64；
- WebView2 已存在和缺失补装；
- 首次安装、覆盖安装、卸载、保留数据后重装；
- 单实例、端口冲突、托盘隐藏、任务运行时退出确认；
- DSH 启动失败、超时、异常退出、主进程崩溃后的子进程回收；
- 官方 WebUI 的模型配置、工作区、长会话、流式输出、工具审批、文件选择和终端；
- 官方新版通知与兼容版通知的去重；
- 下载中断、代理错误、磁盘不足、摘要错误和签名错误；
- 兼容升级、验证副本失败、首次启动失败回滚和手动回退提示；
- 默认界面、沉浸皮肤、适配失败降级；
- 超大图片、损坏图片、原图删除和内部资源协议越权路径；
- 空配置、缺失目录、只读目录、超长路径和非 ASCII Windows 用户名。

发布验收必须同时包含自动化测试、安装器烟雾测试和真实 WebView2 的人工检查。
性能测试记录机器配置、冷/热启动、桌面壳内存、DSH 内存和 WebView2 进程组内存，
不得把多进程重复统计或遗漏。

## 12. 实施约束

实现遵循最小改动和清晰边界：窗口、进程、更新、皮肤、配置与日志各自保持单一
职责，通过类型化接口通信。新增生产依赖必须在实施前列出名称、用途和替代方案，
取得用户确认后再加入。

实现阶段需要先生成分步骤实施计划，再按测试驱动方式完成。任何删除旧版本、快照、
皮肤或用户数据的实际操作都必须由用户在界面中明确触发并确认。
