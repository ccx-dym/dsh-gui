# 毛玻璃强度设置设计

## 背景

当前沉浸式皮肤始终使用一张由桌面壳托管的背景图片。已有“背景模糊”只处理图片层，近期实验样式则为侧栏、详情栏、输入卡片和标题栏写死了不同的 `backdrop-filter` 数值。中央工作区仍主要直接显示背景，用户无法统一控制整个 DSH 主界面的毛玻璃强弱，也无法明确关闭毛玻璃而保留背景图。

本次改动把毛玻璃强度提升为独立皮肤设置。背景图片继续只有一个绘制层；图片自身模糊与界面玻璃模糊保持两个互不耦合的参数。

## 目标

- 外观设置页新增“毛玻璃强度”滑块，范围为 `0px` 至 `32px`。
- 既有设置升级后的默认值为 `0px`，不改变升级前的视觉结果。
- 中央工作区、侧栏、详情栏、输入卡片和自绘标题栏使用同一个毛玻璃强度。
- 强度为 `0px` 时不应用毛玻璃专用模糊、高光或阴影，但仍保留背景图及既有图片设置。
- 背景图片继续使用唯一画布，不为任何面板复制图片或单独计算背景位置。
- 设置保存、恢复默认、进程重启和 Schema 迁移均保持一致。

## 非目标

- 不移除或改变既有“背景模糊”设置；它继续只控制图片层。
- 不新增面板透明度设置，也不允许分别调节各区域的玻璃强度。
- 不把弹窗、菜单、审批或危险确认改成低可读性的透明表面。
- 不扩大皮肤适配器支持的 DSH 版本或远程页面权限。
- 不改变背景图导入、托管协议、图片摘要或内容安全策略。

## 方案选择

采用独立字段 `glass_blur_px`，贯穿 Rust 持久化模型、Tauri 线协议、TypeScript 编辑状态和 DSH 注入适配器。字段使用闭区间 `0..=32` 的整数，避免浮点序列化差异，并与既有 `blur_px` 的单位保持一致。

未复用 `blur_px`，因为图片本身模糊与界面背板模糊是不同视觉操作，复用会使两者无法独立调节。未把参数保存在第二份客户端配置中，因为这会破坏保存、恢复默认、版本迁移和事件同步的原子性。

## 设置模型与迁移

### Schema 2

皮肤持久化文档升级为 Schema 2，`settings` 增加：

```json
{
  "glass_blur_px": 0
}
```

Schema 2 严格拒绝未知字段，`glass_blur_px` 必须是 `0..=32` 的整数。新建默认设置和“恢复默认”均写入 `0`。

### Schema 1 迁移

读取 Schema 1 时执行内存迁移：保留原有沉浸模式、图片摘要、填充方式、位置、背景模糊、遮罩和图片不透明度，并补充 `glass_blur_px = 0`。迁移后的下一次成功保存以 Schema 2 原子替换旧文件。

不在只读加载阶段主动改写磁盘，避免应用仅启动或设置文件损坏时产生隐式写入。未知 Schema、越界值、非整数及未知字段继续按损坏设置分类并失败关闭。

## 前端编辑体验

外观设置页在“背景模糊”之后增加“毛玻璃强度”滑块：

- 标签：`毛玻璃强度`；
- 范围：`0` 至 `32`；
- 步长：`1`；
- 输出：`Npx`；
- `0px` 表示关闭毛玻璃；
- 滑动时只更新本地草稿和预览，点击“保存外观”后才提交到主窗口。

预览区域继续只创建一个背景节点。预览内容层根据草稿值切换玻璃样式：大于零时使用对应的 `backdrop-filter` 和 `-webkit-backdrop-filter`；为零时清除毛玻璃专用滤镜、高光与阴影。忙碌、保存失败、陈旧 revision 和外部设置事件沿用现有 reducer 与操作序号语义。

## DSH 主界面渲染

### 唯一背景层

现有 `body::before` 继续绘制唯一背景图片，并独立应用 `blur_px`、图片不透明度、填充和位置。`body::after` 继续绘制浅色或深色可读性遮罩。任何 DSH 面板都不得重新引用背景图片 URL。

### 统一玻璃强度

精确绑定 DSH `0.1.1-rc.2` 的适配器把 `glass_blur_px` 应用于：

- `.pI_x6G_centerCol` 中央工作区；
- `.pI_x6G_sidebarCol` 左侧栏；
- `.pI_x6G_detailsCol` 右侧详情栏；
- `[data-composer-card]` 输入卡片；
- `#dsh-desktop-titlebar` 自绘标题栏。

这些选择器属于当前精确版本的已验证 DOM/CSS 合约，不扩大到未知类名或通配业务节点。所有区域使用完全相同的模糊半径；半透明染色可按区域使用固定层级，以保持导航、正文和输入区的边界，但不得从强度值派生不同模糊半径。

当 `glass_blur_px > 0` 时，上述区域设置：

- `backdrop-filter: blur(Npx) saturate(1.28)`；
- 等价的 `-webkit-backdrop-filter`；
- 固定的半透明背景、细边缘高光和克制阴影。

当 `glass_blur_px = 0` 时，生成脚本不包含这些区域的 `backdrop-filter`、玻璃专用高光或玻璃阴影。中央区和既有透明区域继续直接显示同一张清晰背景图；弹窗、菜单、审批和危险确认继续使用较高不透明度的官方或适配层表面。

## 数据流

1. Rust `SkinStore` 加载 Schema 1 或 Schema 2，生成带 `glass_blur_px` 的类型化设置。
2. Tauri 外观命令把字段放入现有皮肤 envelope，前端 reducer 建立草稿。
3. 用户移动滑块时，预览仅从草稿渲染，不修改持久化状态或主窗口。
4. 用户保存时，前端把完整草稿和 expected revision 一次提交。
5. Rust 校验全部字段并原子保存 Schema 2，revision 单调递增。
6. 皮肤状态事件发布后，主窗口使用新设置重新生成一次适配脚本。
7. 页面导航、关闭沉浸模式或适配失败时，现有清理脚本撤销桌面壳拥有的皮肤样式。

## 类型与兼容性

- Rust `SkinSettings`、持久化 DTO、草稿 DTO 和相关视图类型新增边界明确的 `u8` 字段。
- TypeScript wire 类型与编辑状态新增 `glassBlurPx: number`，所有入口继续通过 reducer 的显式夹取或 Rust 校验保护。
- 公共函数和 Tauri 命令保持完整类型注解；不新增全局可变状态。
- 旧版字段 `panel_opacity_percent` 继续承载图片不透明度，不借此保存毛玻璃强度。
- 精确 DSH 适配器版本和签名兼容门禁保持不变。

## 错误处理与安全

- 越界、非整数、未知 Schema 或未知字段不得进入注入脚本。
- 动态 CSS 值只来自已验证的 `u8`，脚本不得拼接任意用户文本。
- 皮肤图片无效、沉浸模式关闭、来源不可信或 DOM 合约失败时，继续使用固定清理脚本失败关闭。
- 设置保存失败时保留当前已提交设置，前端显示固定错误文案，不回显路径或底层错误。
- 迁移不读取网络、不修改 runtime、不触发数据库或外部服务操作。

## 测试策略

实现遵循 Red-Green-Refactor，每项生产行为先由失败测试锁定。

### Rust

- Schema 1 读取后得到 `glass_blur_px = 0`，原字段完整保留。
- Schema 2 对 `0` 和 `32` 接受，对 `33`、负数、非整数和未知字段拒绝。
- 默认设置与恢复默认均为 `0`。
- 保存迁移后的设置写出 Schema 2，并保持 revision 语义。
- 适配器可执行脚本在 `0` 时不产生玻璃滤镜，在 `1` 和 `32` 时对五个验证区域使用精确同值。
- 清理、来源门禁、版本门禁和图片层唯一性继续回归。

### TypeScript

- wire 转换、初始状态、reducer 与保存 payload 保留 `glassBlurPx`。
- 滑块范围、标签、单位和实时输出正确。
- `0` 时预览移除玻璃滤镜与专用装饰，正值时只作用于内容层而非背景图片节点。
- 陈旧事件、并发操作、保存失败和恢复默认行为保持不变。

### 完整验证

- `cargo fmt --all -- --check`；
- 相关 Rust 定向测试与 `cargo test --locked`；
- `cargo clippy --locked --all-targets -- -D warnings`；
- `pnpm test`；
- `pnpm build`；
- 生产版构建；
- Windows WebView2 实际检查 `0px`、`16px` 和 `32px`，覆盖首页、普通会话、侧栏展开/收起、详情栏和输入卡片。

## 验收标准

1. 主窗口始终只显示一张连续背景图，标题栏、侧栏、中央区和详情栏之间没有图片错位或重复。
2. 毛玻璃滑块范围为 `0..=32px`，默认和 Schema 1 迁移结果均为 `0px`。
3. `0px` 时背景图保持清晰，主界面不存在毛玻璃专用模糊、高光或阴影。
4. 正值时五个验证区域使用相同模糊半径，滑动预览和保存后的真实 DSH 页面结果一致。
5. “背景模糊”和“毛玻璃强度”互不影响，可以独立组合。
6. 弹窗、菜单、审批和危险确认保持可读，不因全局通配选择器变透明。
7. 关闭皮肤、图片无效、版本不兼容或 DOM 合约失败时完整恢复官方样式。
8. 旧设置、背景图及用户数据在迁移、保存和恢复默认流程中不丢失。
